# 章节精读 · SOLID 五原则（p.51–67）

> 书摘。原文用 > blockquote 引用，感想用普通段落。

## 章节定位

- 书：《深入设计模式》
- 章节：第 2 章 SOLID 原则，p.51–67（S/O/L/I/D 分别在 p.52/54/57/63/66）

## 原文摘录（用自己的话转述）

### S · SRP（p.52）单一职责
> 一个类只应该有**一个**让它需要改变的理由。
>
> 这条原则常被误解为"一个类只做一件事"——其实更准确的版本是：**"一个类只服务一个'行为者'"**（actor）。
>
> 例如 `Employee` 类同时被财务部门（关心 salary）和 HR 部门（关心 vacation）用 → 两个行为者 → 应该拆。

### O · OCP（p.54）开闭
> 类对**扩展**开放，对**修改**关闭。
>
> 关键：在不改动已有代码的前提下，**通过新增代码**来扩展行为。
>
> 实现手段：**抽象**（接口/抽象类）+ **多态**。把变化的部分抽出来，让不变的部分依赖抽象。

### L · LSP（p.57）里氏替换
> 子类必须**完全**替换父类，而不破坏客户端行为。
>
> 反例：`Square extends Rectangle` 时，`Rectangle.setWidth/setHeight` 在 Square 里"反直觉"——这就是 LSP 被破坏。
>
> 实务上：所有继承的方法必须"语义保留"；做不到就用组合。

### I · ISP（p.63）接口隔离
> 客户端**不应该**被迫依赖它们用不到的方法。
>
> 胖接口（10+ 方法）会让客户端被迫看到不关心的 API → 拆成小接口，按客户端需求切。
>
> 注意：ISP 和 SRP 都讲"小"，但 SRP 针对**类的实现**，ISP 针对**类的接口**。

### D · DIP（p.66）依赖倒置
> 高层模块**不应该**依赖低层模块，两者都应该依赖**抽象**。
> 抽象**不应该**依赖细节，细节应该依赖抽象。
>
> 直白版：所有依赖都用接口/抽象类，**别 import 具体实现**。
>
> 通俗版："**所有权反转**"——上层模块（业务规则）定义接口，下层模块（实现）依赖上层接口。

## 我用自己的话说

这一章给我的最大启示是：**SOLID 不是五条独立规则，而是一条递进的认识链**。

| 顺序 | 原则 | 解决什么问题 |
|---|---|---|
| 1 | SRP | 类太大 → 拆 |
| 2 | OCP | 改需求要动老代码 → 用接口隔离变化 |
| 3 | LSP | 抽象可靠 → 子类替换不被破坏 |
| 4 | ISP | 接口太大 → 按客户端切 |
| 5 | DIP | 依赖具体实现 → 依赖抽象 |

读完后回想本仓库 `gz168` 的设计，会发现 **23 个模式就是这 5 个原则的具体应用**：
- `Strategy`/`Adapter`/`Bridge` 是 OCP+DIP 的体现
- `Decorator`/`Proxy` 是 LSP+OCP 的体现
- `Facade` 是 ISP（提供瘦接口）
- `Template Method` 是 OCP（钩子扩展）

所以"学模式"不如"先学原则"——原则搞清了，模式就是工具；原则没搞清，模式就是咒语。
