# 章节精读 · Factory Method 与 Abstract Factory（p.72 / p.86）

> 书摘。原文用 > blockquote 引用，感想用普通段落。

## 章节定位

- 书：《深入设计模式》
- 章节：第 3 章 创建型模式 · Factory Method（p.72）/ Abstract Factory（p.86）

## 原文摘录（用自己的话转述）

### Factory Method · p.72
> **意图**：把"对象的创建"延迟到子类。父类只定义抽象方法（`createProduct()`），由子类决定到底 `new` 哪个具体类。
>
> 关键：**不是**"返回一个静态工厂"那么简单。它的本质是**用继承 + 多态把"new 操作符"委托给子类**。
>
> 经典结构：
> ```
> Creator（抽象）
>   ├── factoryMethod(): Product   ← 钩子，子类实现
>   └── anOperation() { product = factoryMethod(); ... }
> ConcreteCreatorA / B             ← 各自返回 ConcreteProductA / B
> ```
>
> 何时用：当你**不能预判**要创建哪种对象，但父类需要稳定逻辑时。

### Abstract Factory · p.86
> **意图**：创建**一族**相关对象，而不指定具体类。
>
> 例：UI 主题工厂 —— 同一个 Factory 接口，可以返回 WindowsFactory → WindowsButton + WindowsCheckbox；或 MacFactory → MacButton + MacCheckbox。
>
> 关键："一族"——保证按钮和复选框**风格一致**（都是 Windows 或都是 Mac）。
>
> 与 Factory Method 的区别：Factory Method 创建**一个**对象；Abstract Factory 创建**一族**互相关联的对象。

## 我用自己的话说

读完这两章的最大收获：**工厂模式不是"代替 new"的小聪明，而是处理"变化来自创建细节"的设计工具**。

把它落到本仓库 `gz168`，能清晰看到三种"创建风格"：

#### 1. Laravel 容器 = 完美 Abstract Factory
Laravel 的 `$this->app->singleton(NavRegistry::class, fn($app) => ...)` 本质就是抽象工厂：
- 容器是抽象（`Illuminate\Contracts\Container\Container`）
- 业务接口是产品族（`NavRegistry`/`NavResolver`/`VisibilityChecker` 是一族"导航解析"产品）
- 容器返回这族产品时，保证**实现一致**（要么都绑 DefaultVisibility，要么都绑 RolePermissionAwareVisibility）

这正好对应书里"创建一族相关对象"——只是书里叫"Windows 工厂/ Mac 工厂"，本仓库叫"默认配置工厂/ 权限感知配置工厂"。

#### 2. `FrontNav::packageRegistered()` = Factory Method 模板
```php
$this->app->singleton(NavRegistry::class, function (Application $app): NavRegistry {
    // 这个闭包就是 factoryMethod：返回 NavRegistry 产品
    return new InMemoryNavRegistry(...);
});
```
外部（容器）调用 `factoryMethod`（闭包），决定具体 `new` 哪个实现。

#### 3. `ChannelPushDispatcher` 遍历 `$adapters` = Abstract Factory 的批量产品
不像传统 Abstract Factory 用"一个工厂返回一族产品"，`ChannelPushDispatcher` 用**注册表 + foreach**：
- 注册表（容器注入）= Abstract Factory
- `foreach ($this->adapters as $adapter)` = 创建一族"平台适配器"
- `foreach ($this->adapters)` 上一节已被我用 OCP/DIP 解读过

这其实是 Abstract Factory 的**变体**——把"工厂调用"展开成"枚举工厂产物"。本质没变：**保证产品族内部一致**（都是 `ChannelInventoryAdapter` 子类）。

## 行动计划 / One Thing

- [ ] 在 code review 时，对照 Factory Method 问自己："这个 `new` 操作符要不要移到子类的钩子？"——可能的话，把变化抽出去
- [ ] 当"创建一族对象"出现时（Laravel 容器里常见），对照 Abstract Factory 检查产品族的一致性
- [ ] 工厂模式和 Service Provider 边界模糊时，看返回类型是不是接口——是则工厂；是具体类则可能漏了 DIP
