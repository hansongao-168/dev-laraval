# 设计模式落地 · gz168 模块化架构

## 一句话

> 本仓库 `gz168` 是一个模块化 Laravel 多包架构，GoF 23 模式在这里不是"为了用而用"，而是模块解耦的自然产物；读懂了契约 + 容器 + 事件，就读懂了这些模式。

## 是什么

`gz168/` 是主仓库的子模块，内含几十个业务模块（FrontNav / Customer / RolePermission / Purchase / Inventory …），它们通过 **契约（接口）+ ServiceProvider + 容器 + 事件** 协作。设计模式集中体现在 FrontNav（前端导航）、module-core（模块加载）、common（公共底座）、RolePermission（角色权限）四者中。

## 为什么重要

- 新增业务模块（如 `DemoConsumer`）**不改动 FrontNav 任何一行代码**即可接入——这是开闭原则 + 依赖倒置的直接结果。
- 接口契约让"数据库版 Registry"等未来替换成为可能，而业务模块零感知。

### 核心：契约驱动（依赖倒置 D）

五个接口把模块依赖全部反转成"面向接口"：

```
NavItem（不可变值对象）← 所有模块共用
NavRegistry（注册导航项）← FrontNav 提供默认实现
NavRegistrar（pull 模式声明组/位置/items）
VisibilityChecker（可见性策略）
Authorizable（角色权限 duck-typing 契约，RolePermission 提供）
```

关键例子——`Customer` 走 **pull 模式**（容器绑 `NavRegistrar`，FrontNav 启动时发现），`DemoConsumer` 走 **push 模式**（直接调 `NavRegistry::group()`），两模式共存于同一 registry，互不冲突。这正是"对扩展开放、对修改关闭"。

### 数据流全景（模式协同）

```
ModuleLoader (模板方法：依赖排序→注册 provider→回调)
   │
   ▼
FrontNavServiceProvider (工厂/单例：创建 NavRegistry/NavResolver/VisibilityChecker)
   │
   ▼ 业务模块经契约注册
NavResolver (门面：编排 过滤→权限→成树→排序→缓存)
   │  ├─ VisibilityChecker (策略)
   │  └─ CacheRepository (代理)
   ▼
NavController → NavItemResource (适配器：统一 JSON)
   │
   ▼
packages/front-nav labels.js (装饰器：叠加 i18n 翻译)
```

## 易错 / 注意

- **契约是最小集**：`NavRegistrar` 只声明 `group()/location()/items()`，加方法会破坏所有实现方。
- **事件是异步失效信号**：`NavStructureChanged` 只做缓存失效 + 审计日志，不承载业务数据搬运。
- **Proxy 与 Decorator 别混**：缓存是"控制访问"，翻译是"增强展示"。
- **模块启动顺序**：module-core 用拓扑排序（`sortByDependencies`）处理 `requires`，循环依赖会抛异常。
