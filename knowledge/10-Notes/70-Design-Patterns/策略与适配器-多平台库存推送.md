# 策略 + 适配器：多平台库存推送（ChannelInventoryAdapter）

## 一句话

> **策略模式** = 定义一族可互换算法，运行时选一个；**适配器模式** = 把不同平台 API 统一到同一接口。本仓库 `ChannelInventoryAdapter` 是两者结合：一套接口统一 Amazon/Shopify/TikTok 库存读写，按 `supports()` 在运行时选择平台策略。

## 是什么

### 问题：多平台库存推送

一个 `ChannelListing`（商品上架记录）可能挂在 Amazon（FBA/MFN）、Shopify、TikTok 等平台。每个平台 API 完全不同（REST/GraphQL、鉴权、库存语义）。如果不抽象，`ChannelPushDispatcher` 会变成 if-else 堆叠的上帝类。

### 解：接口 + 注册表 + 策略选择

```
interface ChannelInventoryAdapter
    ├── supports(ChannelListing): bool      ← 该适配器认领此 listing 吗
    ├── pushAvailable(listing, qty)         ← 推送可用库存
    └── fetchPlatformQuantity(listing, forceRefresh) ← 读取平台实时库存

实现（策略）：
    ├── AmazonFbaInventoryAdapter   (只读，FBA 走入库单)
    ├── AmazonMfnInventoryAdapter   (MFN 自发货)
    ├── ShopifyInventoryAdapter     (GraphQL InventorySetQuantities)
    └── TikTokInventoryAdapter
```

### 关键：`ChannelPushDispatcher` 如何选策略（`ChannelPushDispatcher.php`）

```php
public function push(ChannelListing $listing, int $targetQty, ...): InventoryPushResult
{
    foreach ($this->adapters as $adapter) {           // 注册表遍历
        if (! $adapter->supports($listing)) {          // ← 策略认领
            continue;
        }
        $result = $adapter->pushAvailable($listing, $targetQty);
        return $this->logPush(...);                    // ← 统一日志/重试/通知
    }
    return InventoryPushResult::skipped('No adapter supports this listing.');
}
```

要点：
- `$adapters` 是 `iterable`（构造注入），由容器把所有 `ChannelInventoryAdapter` 实现聚合注入——这是**注册表 + 策略模式**。
- `supports()` 相当于策略的"适用条件"，让每个策略自决，调度器不关心平台差异。
- 调度器统一处理后事（写 `InventoryPushLog`、失败重试、失败通知），**策略只管"怎么推"**——职责分离。

### Adapter 的适配作用（`ShopifyInventoryAdapter.php`）

```php
class ShopifyInventoryAdapter implements ChannelInventoryAdapter
{
    use CachesPlatformQuantity;   // ← trait 复用（组合替代继承）

    public function pushAvailable(ChannelListing $listing, int $quantity): InventoryPushResult
    {
        // 调用 Shopify GraphQL mutation（内部封装平台差异）
        $data = $this->client->query($store, self::SET_QUANTITIES_MUTATION, [ ... ]);
        // 统一返回 InventoryPushResult，不泄漏平台异常
        return InventoryPushResult::completed($previousQty ?? 0, $quantity);
    }
}
```

适配器把"Shopify 的 GraphQL 细节""Amazon 的 SKU 约束""TikTok 的 API"全部翻译成 `InventoryPushResult` 这一个统一返回类型——这正是 **Adapter 模式**"转换接口"的本质。

## 为什么重要

- **开闭原则**：新增平台 = 新增一个 `implements ChannelInventoryAdapter` 的类 + 容器注册，**零改动调度器/对账服务**。
- **平台差异隔离**：业务层（对账、报警、补货）只看 `InventoryPushResult`，不碰平台 API。
- **测试友好**：`InventoryReconcileService`/`ChannelPushDispatcher` 注入 mock 适配器即可单测，无需真平台。

## 怎么用 / 怎么实现（复用套路）

1. 定义一个领域接口，方法 = 平台无关的业务动词（`pushAvailable`、`fetchPlatformQuantity`）。
2. 每个平台写一个实现类，内部封装平台 SDK。
3. 构造注入 `iterable $adapters`，调度时用 `supports()` 认领。
4. 统一 DTO（`InventoryPushResult`）作为适配器的"标准电压"。
5. 失败处理（重试/退避/断路器）放在调度层，不进适配器。

### 相邻概念：重试 = 保护代理（`InventoryPushRetryService`）

- `mayAutoPush()` = 连续失败数 < 上限（`consecutiveFailureCount`）
- `pushCircuitOpenListingIds()` = 找出断路器"打开"的 listing
- `scheduleRetry()` + `delaySecondsForAttempt()` = **指数退避**（`[60,120,300,600,900]`）

这是 **Proxy（保护代理）** 的思想：在真正调平台 API 前先判断"该不该放行"，熔断降级。与装饰器（增强）不同，代理是"控制"。

## 易错 / 注意

- `supports()` 必须**可快速判断**，不要在 supports 里发起网络请求。
- 适配器之间要**互斥**：`ChannelPushDispatcher` 用第一个 `supports()` 命中的适配器，两个都返回 true 会顺序截断（第一个赢）。
- 平台异常要在适配器内捕获并翻译成 `InventoryPushResult::failed(...)`，不能抛到调度层。
- `InventoryPushResult` 是跨平台契约，加字段会波及所有实现。
