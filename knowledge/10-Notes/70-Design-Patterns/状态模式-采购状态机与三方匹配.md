# 状态模式：采购状态机与三方匹配（PurchaseOrderStatus / ThreeWayMatch）

## 一句话

> **状态模式** = 把"对象在不同状态下行为不同"抽成显式状态，状态转换由状态对象自己决定。PHP 8.1 枚举让这更简洁：本仓库用 `enum` 表达采购/发票/三方匹配的状态机，用纯函数 `resolveStatus()` 做状态判定。

## 是什么

### 经典状态机 vs 本项目实现

经典 GoF 状态模式：`Context` 持有 `State` 对象，`State` 接口有 `handle()`，状态内部决定下一个状态（如文档审阅：Draft→Review→Approved）。

本仓库更轻量：**用 enum + 纯判定函数**表达状态机。这是状态模式的一种"类型安全"变体——状态集合固定、转换规则集中在一个纯函数里。

### 采购订单状态机（`PurchaseOrderStatus`）

```php
enum PurchaseOrderStatus: string implements HasLabel
{
    case Draft = 'draft';
    case PendingApproval = 'pending_approval';
    case Approved = 'approved';
    case PartiallyReceived = 'partially_received';
    case Received = 'received';
    case Cancelled = 'cancelled';

    public function getLabel(): ?string   // ← 状态自带展示（Filament HasLabel）
    {
        return match ($this) {
            self::Draft => '草稿',
            self::PendingApproval => '待审批',
            self::Approved => '已批准',
            self::PartiallyReceived => '部分收货',
            self::Received => '已收齐',
            self::Cancelled => '已取消',
        };
    }
}
```

要点：
- **状态自带行为**（`getLabel()`）——状态对象不再只是字符串，而是携带语义。
- **转换规则**由业务 Service 集中控制（下单→待审批→审批→收货），不散落在各处 if。
- **类型安全**：传参、匹配都是 enum，杜绝拼写错误（`'pending_approv'`）。

### 三方匹配状态机（`ThreeWayMatchLineStatus` + 纯函数判定）

`PurchaseThreeWayMatchService::resolveStatus()` 是**状态判定的纯函数**：

```php
public function resolveStatus(int $orderedQty, int $receivedQty, int $invoicedQty): ThreeWayMatchLineStatus
{
    if ($invoicedQty > $receivedQty) {
        return ThreeWayMatchLineStatus::OverInvoiced;     // 超开票
    }
    if ($receivedQty < $orderedQty) {
        return ThreeWayMatchLineStatus::PendingReceive;   // 待收货
    }
    if ($invoicedQty < $receivedQty) {
        return ThreeWayMatchLineStatus::PendingInvoice;   // 待开票
    }
    return ThreeWayMatchLineStatus::Matched;              // 已对齐
}
```

三个数量（下单/收货/开票）=> 四种状态，判定规则**全部集中在这一个函数**。`statusSummaryFor()` 汇总各类别计数、`exceptionCountFor()` 统计非 Matched 行——它们都**复用同一个 `resolveStatus`**，不会出现"这里一种算法、那里另一种算法"的漂移。

### 配套 Enum（同类设计）

- `SupplierInvoiceStatus`（含 `invoicedForMatching()` 静态方法：返回"参与匹配"的发票状态子集）
- `PurchaseRequestStatus`、`PurchaseReceiptSource`、`Alibaba1688ReconciliationStatus`、`ApAgingBucket`、`SupplierPlatform` …

全部是 `enum: string`，配合 Filament 的 `HasLabel`/`HasColor`，一个枚举同时服务：存储值、展示文案、颜色、状态转换。

## 为什么重要

- **把散落的 if 收敛成一处**：三方匹配的判定只存在于 `resolveStatus()`，改规则只改一处。
- **状态可枚举、可穷举**：`match` 强制覆盖所有 case，新增状态会漏掉 compiler 检查。
- **展示与逻辑解耦**：`getLabel()/getColor()` 服务 Filament，业务 Service 只看 value。
- **测试简单**：`resolveStatus` 是纯函数，边界（恰好相等/超开票）直接单测。

## 怎么用 / 怎么实现（套路）

1. 用 `enum X: string` 定义状态集合，`implements HasLabel`（Filament 场景）。
2. 状态相关但**不涉及具体上下文**的判定写成纯函数（如 `resolveStatus(q1,q2,q3)`）。
3. 查询/过滤用 `->value` 或枚举集合（如 `invoicedForMatching()` 返回参与子集）。
4. 需要"状态对象行为"（如各状态可执行动作不同）时，升级到 GoF 经典 State：接口 + 每个状态一个类。

## 易错 / 注意

- enum 不是"隐藏 if 的黑魔法"——状态**转换路径**（谁能从 A 到 B）仍需单独验证，别以为枚举就安全。
- 不要在一个 enum 里塞太多业务；`getLabel()` 做展示尚可，复杂行为应考虑独立 State 类。
- `match` 对新增 case 是"漏报"不是"报错"：加了 case 忘了加 match 分支会静默返回 null 或报 TypeError，注意测试覆盖。
- 枚举值（wire 值）一旦上线就**不可改名**（数据库已存 `'pending_approval'`），新增可以、改名不行。
