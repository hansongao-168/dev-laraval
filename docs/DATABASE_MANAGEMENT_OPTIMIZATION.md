# 数据库管理优化评估

> 评估日期：2026-08-16  
> 范围：Laravel 13 / MySQL 8 主库、Eloquent 查询、迁移、备份与日常运维  
> 本文只记录现状与建议，不包含代码或数据库变更。

备份、快照、恢复、恢复演练和时间点恢复的详细功能设计见 [数据库备份、快照与恢复功能设计](DATABASE_BACKUP_SNAPSHOT_DESIGN.md)。

## 结论

当前数据库的基础设计并不差：主要关系已有外键，幂等写入普遍有唯一索引支撑，队列、缓存、会话和业务模块也已分表。现阶段最值得优先优化的不是盲目增加索引，而是建立可恢复、可观测、可持续清理的数据库管理闭环。

建议按以下顺序推进：

1. **P0：补齐备份安全与恢复能力**：异地副本、静态加密、校验、恢复演练、RPO/RTO。
2. **P0：建立慢查询与容量基线**：先采集数据，再决定索引和 SQL 优化。
3. **P1：为高增长表制定保留与归档策略**：邮件正文、Webhook payload、补丁、日志、通知、失败任务。
4. **P1：按真实查询形状评估复合索引**，以 `EXPLAIN ANALYZE` 和线上慢查询为准。
5. **P2：完善迁移发布规范、权限分离和数据生命周期自动化**。

当前本地库接近空库：`users` 仅 3 行、`mail_sync_runs` 仅 7 行，当前最大表 `failed_jobs` 也只有约 0.2 MB。这个环境适合核对结构，不足以证明任何性能优化的收益。因此本文把“已确认的管理缺口”和“需要数据验证的候选项”明确分开。

## 已有基础

- 使用 MySQL 8，结构变更由 Laravel migration 管理。
- 主要关联字段已建立外键或索引。
- 多个幂等入口已有唯一约束，例如邮件的 `(mail_account_id, provider_message_id)`、Git Webhook 的 `(repository_id, commit_id)`。
- Laravel 默认队列、缓存、会话表已采用框架推荐结构。
- 已有 `DatabaseBackup` 模块，支持手动/定时全库备份、结构或数据范围、备份数量保留和恢复前备份。
- 数据库凭据由配置读取，本文未读取或记录任何 `.env` 密钥。

## P0：备份与灾难恢复

### 已确认现状

`DatabaseBackup` 当前将 gzip 压缩的 SQL 文件写入 `storage/app/backup`，默认保留 30 份自动备份。备份与恢复依赖本机 `mysqldump`、`mysql`、`gzip`、`gunzip`。这可以应对误操作，但不能单独应对主机、磁盘、账号或勒索软件级故障。

当前实现还需要重点评估以下风险：

- 备份默认与应用位于同一主机/磁盘，没有异地副本策略。
- 未看到备份文件静态加密、校验和或不可变存储策略。
- 保留规则按“份数”而非恢复目标设计，没有日/周/月分层。
- 未形成定期恢复演练、恢复耗时和恢复结果记录。
- 数据库密码作为命令参数组装进 shell 命令；即使未写日志，也应评估进程列表暴露和 shell 边界风险。
- `mysqldump` 命令未显式声明适合 InnoDB 在线一致性备份的参数组合，需要在实现前验证 `--single-transaction`、`--quick` 等选项及锁表影响。

### 建议目标

- 明确恢复目标：建议先以 **RPO 24 小时、RTO 2 小时**作为开发/学习环境基线；若承载真实业务，再按业务等级缩短。
- 使用“本机快速恢复副本 + 异地加密副本”，异地副本至少位于不同故障域。
- 使用日/周/月分层保留，而不是只有固定数量，例如 7 日、4 周、6 月；最终数值按数据敏感度和存储成本确定。
- 每份备份生成 SHA-256 校验和，记录数据库名、schema 版本、开始/完成时间、文件大小、备份范围和工具版本。
- 每月至少执行一次隔离环境恢复演练，验证：解密、解压、导入、migration 状态、关键表行数、受保护管理员不变量和应用健康检查。
- 应用运行账号只拥有写入指定备份目录的权限；备份上传账号只拥有目标桶所需的最小权限。
- 数据库凭据优先通过 MySQL option file、受控环境或进程输入传递，避免出现在命令行参数中。

### 验收标准

- 最近一次成功备份时间可见，备份失败能告警。
- 任取一份异地备份可在隔离库完成恢复，且恢复记录包含耗时和校验结果。
- 删除应用主机上的本地备份后，异地副本仍可恢复。
- 文档化并实际测得 RPO/RTO，不以“任务执行成功”代替“数据可恢复”。

## P0：查询与容量可观测性

### 已确认现状

`AppServiceProvider` 当前没有数据库查询监控配置；代码库中也未发现 `DB::whenQueryingForLongerThan()` 或开发环境 `Model::preventLazyLoading()`。因此出现请求内累计查询过慢或意外 N+1 时，主要依赖人工发现。

### 建议

- 记录请求内累计数据库耗时，并设置分环境阈值。初始阈值可从 300–500 ms 起步，采集一周后按 P95/P99 调整。
- 开发和测试环境启用 Eloquent 懒加载违规告警或阻断；生产环境先记录而非直接抛错。
- 开启并规范使用 MySQL slow query log；生产参数需由运维基于磁盘与隐私要求配置。
- 建立最小看板：连接数、活跃/等待连接、慢查询数量、查询 P95/P99、锁等待/死锁、Buffer Pool 命中率、主库容量、增长速度、备份年龄、队列积压。
- 定期运行 Laravel 的数据库检查命令或等效监控，连接数超过阈值时告警。
- 所有慢查询优化保留优化前后 SQL、绑定参数脱敏样例、`EXPLAIN ANALYZE` 和耗时对比。

### 推荐基线

| 指标 | 初始关注线 | 说明 |
| --- | ---: | --- |
| 单请求累计查询时间 | 300–500 ms | 先观测后按业务调整 |
| 单条慢查询 | 200 ms | 后台报表可单独设更高阈值 |
| 数据库连接使用率 | 70% 告警 | 需结合连接池和任务并发 |
| 备份年龄 | 超过 26 小时告警 | 对应每日备份基线 |
| 磁盘使用率 | 70% 预警、85% 告警 | 同时预测耗尽日期 |

这些数值是启动监控的建议值，不是未经验证的生产 SLA。

## P1：高增长表的数据生命周期

以下表含 `longtext`、JSON、日志或状态历史，数据量增长后会同时影响备份时间、Buffer Pool、索引体积和管理页面：

| 表/类别 | 增长来源 | 建议 |
| --- | --- | --- |
| `mail_inbound_messages` | 邮件正文、HTML、JSON 标签 | 明确保留期；正文/附件评估对象存储，数据库保留检索元数据 |
| `mail_outbound_messages` | 正文、发送错误、重试历史 | 成功记录与失败记录采用不同保留期 |
| `mail_sync_runs` | 每次同步运行记录 | 保留近期明细，长期按日聚合或归档 |
| `git_webhook_events` | payload、changed files、操作状态 | 对成功和失败事件分层保留 |
| `git_commit_files` | content、patch | 评估只保留必要版本，历史大字段转对象存储或压缩归档 |
| `git_commit_file_backups` | 文件应用备份 | 与恢复窗口一致，过期后分块清理 |
| `notifications` | 每用户通知 | 已读和未读设置不同保留期 |
| `failed_jobs` | payload、exception | 失败排查完成后清理，避免长期积累敏感内容 |
| `log_analysis_entries`、`module_setting_logs` | 日志和审计轨迹 | 审计数据与普通运行日志采用不同保留策略 |
| `personal_access_tokens`、`refresh_tokens`、`sessions` | 认证状态 | 定期清理过期或失效记录 |

清理任务应使用 `chunkById` / `lazyById` 或小批量删除，限制单事务行数并避开业务高峰。先归档后删除，审计数据不得套用普通日志的短保留期。涉及真实业务前，必须由数据所有者批准保留期限。

## P1：索引候选项

现有 schema 已有较多合理索引，不能根据列名继续“见字段就加索引”。低选择性的布尔字段单列索引通常收益有限，应与租户/账号、状态和时间组成符合查询左前缀的复合索引。

以下仅为候选，必须先从慢查询或管理页面 SQL 取得真实查询形状，再用 `EXPLAIN ANALYZE` 验证：

| 场景 | 当前结构 | 候选索引方向 |
| --- | --- | --- |
| 单邮箱账号按接收时间倒序分页 | 有 `(mail_account_id, provider_message_id)`、`(needs_attention, received_at)` | `(mail_account_id, received_at, id)` |
| 单账号筛未读/需关注邮件 | 尚无账号 + 状态 + 时间组合 | `(mail_account_id, admin_is_read, received_at, id)` 或 `(mail_account_id, needs_attention, received_at, id)`，按实际高频筛选二选一 |
| 同步运行历史页 | 仅 `mail_account_id` 外键索引 | `(mail_account_id, started_at, id)`；若主要筛状态则评估 `(status, started_at, id)` |
| 待发送邮件扫描 | `status` 单列索引 | `(status, queued_at, id)` |
| Git 仓库事件时间线 | 有 `(repository_id, event_type)` 和单列 `webhook_received_at` | `(repository_id, webhook_received_at, id)` |
| 未读通知按用户时间分页 | 有 `(notifiable_type, notifiable_id)` | `(notifiable_type, notifiable_id, read_at, created_at)` |
| 导出任务按操作者/状态查看 | 仅 `operator_id` 外键索引 | `(operator_id, status, created_at)` |

注意事项：

- 不为每种筛选组合各建一个索引；先覆盖 Top SQL。
- 新复合索引可能使已有前缀索引冗余，需评估后再删除，不能直接删除外键所需索引。
- 大表加索引要评估在线 DDL、锁等待、磁盘临时空间和回滚方案。
- `%关键词%` 模糊查询不会有效使用普通 B-Tree；邮件正文、Git patch 等全文检索应考虑 MySQL FULLTEXT 或外部检索系统，而不是盲目加普通索引。
- JSON 内高频检索字段应先评估生成列 + 索引；不要直接为完整 JSON 内容建立常规索引。

## P1：查询与并发治理

- Filament 列表统一分页、只选择所需列，并按页面关系使用 `with()` / `withCount()`，避免逐行查询。
- 批处理不要对大量数据直接 `get()`；只读流式任务使用 `lazyById()`，边读边改使用 `chunkById()`。
- 多个独立 `count()` 若处于高频接口，评估条件聚合或缓存；低频后台统计无需为了减少查询数牺牲可读性。
- 库存、审批、凭据轮换、同步状态等“先读后写”流程，要逐项确认是否需要事务、条件更新、唯一约束或行锁，防止并发覆盖。
- 外部事件写入必须依赖数据库唯一约束保证最终幂等，不能只依赖应用层 `exists()`。
- 报表、PDF 和导出应优先进入队列；快照或报表查询避免在长事务中执行。

## P2：迁移与发布治理

- 已发布 migration 不回改；所有结构调整新增 migration。
- migration 的 `down()` 默认可逆；不可逆的数据清理或回填必须明确说明并采用前向修复。
- 避免在同一 migration 混合大规模 DDL 与 DML。大数据回填使用可恢复、可重复、可观测的独立命令或 Job。
- 发布前在接近生产数据规模的副本执行 migration，记录耗时、锁影响和额外磁盘需求。
- 对新增唯一索引，先查重和清洗，再建立约束。
- 对外键变更明确 `cascade`、`restrict`、`nullOnDelete` 的业务含义，尤其是审计和财务类数据。
- schema 变更执行前生成备份，但“有备份”不能替代回滚/前向修复方案。

## P2：账号、敏感数据与环境隔离

- Web、队列、migration、备份分别使用最小权限账号；日常应用账号不拥有建表、删表或全库导出权限。
- 生产只允许受控网络来源连接 MySQL，强制 TLS；禁止公开暴露 3306。
- 测试使用独立数据库，禁止测试命令指向生产连接。
- 凭据字段继续保持应用层加密/哈希；同时确认备份、错误日志和 SQL 监控不会泄露明文或绑定参数。
- 对邮件正文、Webhook payload、异常堆栈等可能含个人信息的数据建立访问审计与脱敏规则。
- 定期轮换数据库和备份存储凭据，保留可追踪但不含秘密的轮换记录。

## 建议实施路线

### 第一阶段：一周内完成基线

1. 定义数据所有者、RPO/RTO、保留期和告警接收人。
2. 记录表容量、日增长量、Top SQL、慢查询、连接数和锁等待基线。
3. 核对备份任务是否实际运行，并在隔离环境完成一次恢复。
4. 建立变更前后的 `EXPLAIN ANALYZE` 记录模板。

### 第二阶段：两至四周

1. 增加异地加密备份、校验和、备份失败告警和恢复演练记录。
2. 增加累计查询耗时监控与开发环境懒加载检测。
3. 为高增长表落地第一批保留/归档任务。
4. 只为已确认的 Top SQL 增加第一批复合索引。

### 第三阶段：持续治理

1. 每月复核慢查询、冗余/未使用索引、容量预测和恢复演练。
2. 每季度复核权限、数据分类、保留期和灾难恢复目标。
3. 当单表达到千万级或维护窗口不可接受时，再评估分区、读写分离、归档库或专用检索系统；当前阶段不建议提前引入。

## 后续变更的统一验收清单

- [ ] 有优化前基线和可复现 SQL。
- [ ] 使用脱敏绑定参数执行 `EXPLAIN ANALYZE`。
- [ ] 说明索引写放大、磁盘和锁影响。
- [ ] migration 可在独立测试库执行并有回退/前向修复方案。
- [ ] 运行相关 PHPUnit 测试及数据库集成测试。
- [ ] 未改变受保护管理员和初始化幂等不变量。
- [ ] 未读取、记录或提交 `.env` 密钥。
- [ ] 备份和恢复均经过实际验证，而非只验证文件存在。

## 本次评估边界

本次使用只读方式检查了当前 MySQL schema、索引与表规模，并审阅了迁移、模型查询和备份模块。未执行慢查询采样、`EXPLAIN ANALYZE`、压力测试、备份或恢复，也未修改任何 PHP 代码和数据库结构。因此，文中的具体复合索引均是待验证候选，不应直接批量实施。
